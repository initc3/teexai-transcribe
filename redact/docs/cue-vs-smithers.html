orchestration runtimes

Cue vs Smithers

Two runtimes for composing LLM calls. Cue is an event loop over an observation stream; Smithers is a task DAG executed to completion.

jameslbarnes/cue  ·  smithers-orchestrator  ·  with the shipped examples

Two execution models

Cue — event-driven

A persistent loop over an Observation stream. Cue policies decide which observations wake a model; the model emits an action or passes. State persists across the session.

Smithers — graph

A declarative DAG of Tasks (Parallel / Loop). Runs start → finish; each task is one model call with a typed output. Durable and resumable.

Control flow in Cue is determined at runtime by incoming events; in Smithers it is fixed by the graph you write.

Part 1 · Cue

Cue is one loop

 observation stream ─▶ cue policies decide "wake?" ─▶ woken program shows the model
                                                      rolling state + eligible tools
                                               ─▶ model emits a tool call OR observe.pass
                                               ─▶ decision recorded (DecisionHistory / memory)
  • No turns. Everything — a transcript line, a video frame, an audio reading, a clock tick — is an Observation on one stream.
  • harness.ingest(obs) is the only entry point. Every cue runs; the ones that fire wake matching programs.
  • observe.pass is first-class — most events are non-events. The value is catching the important moment while avoiding dumb wake-ups.

Cue primitives

primitivewhat it is
Observationtimestamped input: transcript.segment, vision.frame, signal.value, tick
Cue policya "wake?" detector: maybeCue(obs, state) → Heartbeat | undefined. Many run concurrently, at different timescales.
Program + triggerthe model (e.g. GLM-flash) that runs on selected cues (Triggers.onCue("text"))
Tool / observe.passthe structured action it emits — or the first-class "do nothing"
DecisionHistory / WeightedMemoryprior calls + recency-weighted facts, surfaced to the next wake-up → an accumulating, stateful agent

A cue is just an object with one method — fully customizable: tune params, or write your own in ~15 lines.

The cue zoo = clocks at different timescales

Multiple cues run at once. Each catches a different kind of moment — a fast keyword lane and a slow summary lane live in the same harness.

How audio / text / frames map in

Two streams — the harness only ever sees the second

 raw input            PROVIDER (adapter)        observation stream      CUES → model
 ─────────            ──────────────────        ──────────────────      ───────────
 audio bytes ───────▶ TranscriptionProvider ─▶ transcript.segment ────▶ ingest()
 video frames ──────▶ VLMProvider ──────────▶ vision.description
 prosody / probes ──▶ signal source ────────▶ signal.value
 already-have text ─▶ (none) ───────────────▶ transcriptObservation(text)
  • The harness has no idea what audio or tokens are — a provider normalizes every modality to one Observation shape.
  • Providers emit interim hypotheses (isFinal:false) and settled text (isFinal:true); cues like Punctuation ignore interims → you control granularity.
  • Cues tick on observations, not wall-clock — feed tick_observation() as the clock so silence/interval cues fire when the room is quiet.

The shipped examples = one cue → one tool

Each example is the same harness with a different cue and a single action tool. The cue choice is the design.

Speech coaching: wake only on the word "but", propose a "yes-and" rewrite.

Drive a visual from prosody — woken by energy, not words.

live-dashboard

but-coach, in full

new CueHarness({
  cues: [new TextCue(["but"])],            // wake only on "but"
  programs: [{
    name: "but-coach",
    llmProvider: new CerebrasLLMProvider({ /* system + buildUserPrompt */ }),
    allowedTools: ["coach.interrupt_for_but"],
    triggers: [Triggers.onCue("text")],          // run this program when the text cue fires
  }],
  tools: [butFeedbackTool()],                  // schema forces {quote, feedback, alternative, severity}
})

Everything else passes. The alternative field forces a yes-and reframe of the sentence. Restraint is the whole point — and the thing Cue is for.

Cue's scarce resource: model calls

State is bounded by design (fixed-size deques). The one thing you ration is LLM invocations — every wake is one call (cost, latency, rate limits).

levermechanism
cue selectivityWordCountCue(24)/IntervalCue(12) ≪ per-segment — the primary throttle
cooldownscue + tool cooldownSeconds suppress re-fires
observe.passa wake needn't produce an action
coalescemulti-cue on one obs → one call, not N
window / max tokenstranscriptWindowChars, maxCompletionTokens bound per-call cost

We measured this: waking on every segment → ~8s/call and 429s. The fix is exactly cue selectivity + cooldown.

Part 2 · Smithers

Smithers is a declarative DAG

const { Workflow, Task, smithers, outputs } = createSmithers({
  notes: notesSchema, judgment: judgeSchema,        // typed outputs (zod)
});

export default smithers((ctx) => (
  <Workflow name="redactbench">
    <Parallel maxConcurrency={2}>            // stage 1: generate notes 2 ways
      {variants.map(([v,ag]) => <Task id={`gen:${v}`} output={outputs.notes} agent={ag}>…</Task>)}
    </Parallel>
    <Parallel maxConcurrency={8}>            // stage 2: judge each strike + each must-keep
      {leak & keep tasks, reading notes via ctx.outputMaybe(...)}
    </Parallel>
  </Workflow>
));

You write the graph. The runtime executes it — durable, resumable, cached — and collects typed results into tables.

Smithers properties

  • Explicit structure — <Parallel>, <Loop>, <Task>. The control flow is on the page.
  • Durable + resumable — every node/attempt persisted to smithers.db; a crash mid-run resumes.
  • Typed outputs — tasks return zod-validated objects, threaded by ctx.outputMaybe(out,{nodeId}).
  • Bounded — it starts, fans out, terminates with a result set.

PC committee workflow

<Parallel> 11 independent reviews </Parallel>
<Loop until={converged}>          // reviewers revise
   discussion rounds              // seeing each other
</Loop>
<Task> area-chair meta-review </Task>

Fan-out → converge → synthesize. The shape you'd never want to hand-drive.

Reactive loop  vs  orchestrated graph

  CUE  (one agent, over time)

   ··obs··obs··obs··obs··obs··▶ t
        │         │
      pass      act
        ╰─ state accumulates ─╯

one stateful loop reacting forever

  SMITHERS (many agents, a plan)

        ┌─▶ gen:v ─┬─▶ leak×n
   start┤          ├─▶ keep×n ─▶ done
        └─▶ gen:a ─┴─▶ …

a finite fan-out, run to completion

Cue is a verb in the present tense; Smithers is a recipe you execute.

When to reach for which

Reach for Cue when…

  • input is a live stream (audio, a meeting, a feed)
  • the question is "should anything happen right now?"
  • restraint matters — silence is the common, correct output
  • you need one evolving, stateful agent

Reach for Smithers when…

  • you have a known set of work to fan out
  • the question is "run all of this, reliably"
  • you want ensembles, retries, resume, caching
  • the result is a collected, scored artifact
Synthesis · our redaction pipeline

They compose

 audio ─▶ CUE (realtime) ─────────────▶ strike contract ─▶ SMITHERS (offline) ─▶ scorecard
          catch the squiggle live              (the seam)         score the fan-out, K runs, in-TEE
          L1: detect / mark                                       L2–L5: classify · decide · compose · assure
  • Cue = the reactive edge: catch live "strike that" + sensitive-in-hindsight, author marks that accumulate (the emergent half of policy).
  • Smithers = the orchestrated core: generate per-recipient notes, judge leak/keep over K runs, attest the result.
  • They meet at the strike contract — same place Cue↔RedactBench meet at the transcript→notes artifact.

Takeaway

Cue organizes AI work along time — reactive, stateful, "decide when to act."

Smithers organizes it along a graph — orchestrated, durable, "run this to completion."

Most real systems want both: a reactive edge feeding an orchestrated core.
